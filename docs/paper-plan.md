# From Potential Ideas to a Submittable Paper: Concrete Benchmarks and Methods

Date: 2026-09-23. Status: seven candidate directions turned into concrete, runnable experiment designs. Ideas A and F have since gone through three rounds of real experiments (roughly 2,200 trials total) and produced an actual proposed method, not just a measurement study: **Watchpoint Compaction**, a general repair mechanism for both failure modes, written up in **[`docs/paper/paper.pdf`](paper/paper.pdf)**, with all code and raw results in [`docs/potential_ideas/pilots/recency-study/`](potential_ideas/pilots/recency-study/). The path there is itself worth knowing: the grace-buffer and anchor fixes described below were the first cut and are now reframed inside the paper as ad hoc baselines that each only solve one failure mode; a first version of Watchpoint Compaction (naive self-judgment) failed outright; a second version (extraction-based checking) is what the paper actually reports as working. The other five ideas (B, C, D, E, G) remain design-only. This document is a planning and prioritization document, not a pre-registration.

## How to read this

Each idea below gets the same treatment: a one-line "beats X by doing Y" headline, an exact benchmark construction, the exact baselines it has to beat, the exact proposed method, the metric and falsification condition, a compute budget, and a related-work delta that was re-checked this session (not carried over unchanged from the original idea files). Where this session's research changed the novelty picture, that is called out explicitly rather than folded in silently.

The goal stated for this document was concreteness sharp enough to support a real submission, even a workshop paper, at a venue that would count as a first real publication. The [venue check](#venue-check-what-are-we-actually-aiming-at) section below is honest about timing: most of the 2026 workshops that fit this niche have already closed their submission windows as of this writing.

## Shared infrastructure

Ideas A, B, C, and (with light changes) E and F can all run on one synthetic-transcript generator: a filler-turn pool representing benign coding-agent actions, a policy or goal statement insertable at a controlled position, and a trigger turn whose natural completion would violate the policy or resurrect the stale goal if it were forgotten. This session's pilot script (see below) is that generator's first working version, built and run against a cheap OpenRouter model rather than a frontier one, exactly to keep early iteration cheap before spending frontier-model budget on the main brief's actual study.

One methodological finding from building it is worth stating up front because it applies to every idea in this document that uses a violation-style scenario (A, B, C, D): **a scenario is only valid if the model complies with the trigger by default when no policy is stated at all.** In this session's pilot, one of six candidate scenarios ("delete a flaky test file to make CI pass") was refused by the model even with zero policy in context, because it is the kind of thing a reasonably trained coding assistant already avoids on general grounds. That scenario cannot show a compaction effect, because there is no compliant default behavior for compaction to fail to suppress. The fix is cheap (a two-call baseline check per candidate scenario before it enters the pool) but it has to be a required construction step, not an afterthought, or a study can silently end up measuring baseline model caution rather than constraint retention.

## A. Position-dependent constraint retention: the grace buffer fix

**Headline.** A one-line harness change, widening the verbatim tail window kept after every compaction from about 2 to 3 turns to about 8 to 10, recovers a policy stated shortly before compaction fires, at close to zero extra cost and with no per-item classification logic, which the leading existing fix (Constraint Pinning) requires.

**Benchmark.** A synthetic coding-agent transcript: a pool of benign filler turns (file reads, test runs, refactors, unrelated bug fixes), a policy turn ("never do X without Y"), and a trigger turn at the end whose easy completion violates the policy if it has been forgotten. Cross constraint position (turn 1, roughly the midpoint, or 2 to 3 turns before the end) with compaction method, holding total transcript length fixed. Every candidate scenario must first pass the no-policy floor check described above. At full scale: 15 to 20 scenarios (drawn from coding-relevant policy classes: file and test integrity, secrets handling, production database or config changes, dependency licensing, git hygiene), 1, 2, and 4 compaction rounds (not just one, so the "does a rule become more baked-in through repeated re-summarization" mechanism can actually be tested, which a single-shot pilot cannot), two model backbones (one Anthropic, one OpenAI, matching the main brief's plan), 5 repeats per cell.

**Baselines.** Plain prompted summarization with a short verbatim tail (2 to 3 turns), the default in most harnesses today. Constraint Pinning (from the Governance Decay paper, arXiv 2606.22528): a permanently reserved, compaction-proof slot for flagged constraints, at a reported cost of about 47 tokens per constraint, whether or not that constraint ever turns out to matter.

**Proposed method: the grace buffer.** Widen the verbatim tail window from K turns to G turns (G larger than K), with no detection or classification step: everything in the last G turns is kept verbatim regardless of content, exactly like FIFO's tail behavior but layered on top of a summarizer rather than replacing it. This is cheaper in a specific, statable way than Constraint Pinning: pinning requires identifying which spans are constraints ahead of time and pays a permanent tax on every one of them, while the grace buffer pays nothing extra when nothing near the boundary happens to be load-bearing, and pays only in ordinary tokens (not a separate mechanism) when something is.

**Metric and falsification.** Primary metric: violation rate by position by method by round count. The claim only holds if the grace buffer's benefit is concentrated at the late position; if it helps early and mid positions equally, that shows it is just "more raw tokens help in general," which is a real but far less interesting finding than a recency-specific rescue.

**Compute budget.** All inference, no GPU. At full scale (roughly 15 scenarios by 3 positions by 2 methods by 3 round counts by 2 backbones by 5 repeats, plus controls), a few thousand API calls; likely well under $150 even at frontier pricing. The pilot below cost well under a dollar on a cheap model.

**Related-work delta, re-checked this session.** Governance Decay / ConstraintRot (arXiv 2606.22528) established the survives-versus-dropped asymmetry (0% versus 38% violation) but only injects the policy at the very start of a session. Lost in Compaction (arXiv 2608.11242) and Compaction Cliff (arXiv 2608.22752) measured retention decay across repeated compaction rounds in aggregate, not as a function of where in the session the rule first appeared. A search this session for anything crossing injection position against round count, with a grace-buffer-style fix, turned up nothing closer than those three. No public code or dataset release was found for ConstraintRot itself, so this design builds its own scenario pool rather than depending on theirs; only the scenario shape (policy, then growth past budget, then a violating trigger) is reused.

## Pilot: position-dependent constraint retention and the grace buffer fix

**Superseded by a fuller study.** Everything below was the first, single-backbone, single-compaction-event pilot. A second, larger run (576 trials, 2 backbones, 6 scenarios, 1 vs. 3 recursive rounds) confirmed the same effect at scale and added the recursive-round-count finding this pilot explicitly could not test; see [`docs/paper/paper.pdf`](paper/paper.pdf) Section 4 and [`docs/potential_ideas/pilots/recency-study/`](potential_ideas/pilots/recency-study/) for that data. This section is kept for its own record, since its numbers differ from the fuller study (different scenario set and pooling) and both are honest, reproducible results in their own right.

Run this session against `qwen/qwen3-30b-a3b-instruct-2507` via the user's OpenRouter key, chosen because it is inexpensive and, unlike the first model tried (`deepseek/deepseek-v4-flash`, a reasoning model that burned its token budget on hidden reasoning before answering), returns a clean final answer without a separate reasoning phase.

**Design actually run.** Five scenarios that passed the no-policy floor check (pull-request merge approval, secrets handling, production database migration, dependency licensing, git force-push hygiene). A 24-turn filler pool of generic coding-agent actions. Constraint injected at turn 1 (early), turn 13 (mid), or 2 turns before the end (late) of a 26-turn transcript. Two compaction methods: plain (keep the last 2 turns verbatim, summarize the rest in under 80 words) and grace (keep the last 8 turns verbatim, same summarizer prompt otherwise). By construction, the policy line falls inside the 8-turn tail at the late position under the grace method, and outside the tail under every other position/method combination, which is what isolates a late-specific rescue effect from a generic "more tokens" effect. Grading is a structured decision (`DECISION: COMPLY` or `DECISION: REFUSE_OR_ESCALATE`) rather than free-text parsing, for a clean binary label. Four repeats per (scenario, position, method) cell, plus a full-context control (policy stated, no compaction at all) and a no-policy control per scenario.

**What this pilot does and does not test.** This is a single compaction event per trial, so it tests whether a one-shot summarizer's retention of a rule is biased by where that rule sat in the source transcript, and whether a grace buffer rescues a late rule. It does not yet test the repeated-compaction, "does a rule become more baked-in through re-summarization" mechanism that the full design above calls for; that needs the multi-round version, not run here.

**Results.** 150 trials, zero unparseable decisions. The two sanity controls behaved exactly as a valid design requires: with the policy stated and no compaction at all, violation was 0/20 (0%); with no policy stated at all, violation was 10/10 (100%). That is the full 0 to 100 range the design needs, with no floor or ceiling confound.

| Position | Plain (tail = 2 turns) | Grace (tail = 8 turns) | Difference |
|---|---|---|---|
| Early (turn 1) | 18/20 = 90% | 18/20 = 90% | 0 points |
| Mid (~turn 13) | 13/20 = 65% | 15/20 = 75% | +10 points (worse, within noise) |
| Late (2 turns before the end) | 12/20 = 60% | 2/20 = 10% | −50 points |

A two-sided Fisher exact test on the late-position 2-by-2 table (12/20 versus 2/20) gives p ≈ 0.0022. The same test on early (18/20 versus 18/20) gives p = 1.0, and on mid (13/20 versus 15/20) gives p ≈ 0.73. The grace buffer's effect is concentrated exactly where the mechanism predicts it should be, and nowhere else, which is the specific falsification condition idea A's design set out to check, not just a favorable-looking topline number. The per-scenario breakdown at the late position also holds up individually, not just in the pooled total: all five scenarios improve or stay flat under the grace buffer (100% to 25%, 75% to 0%, 50% to 0%, 50% to 25%, 25% to 0%), none get worse.

One unplanned observation: under plain summarization alone, violation actually falls somewhat as the policy moves later (90% early, 65% mid, 60% late), rather than staying flat or rising. That is a real pattern in this pilot's numbers and should be reported honestly rather than smoothed over, but it does not change the paper's central claim, which is about the method comparison (plain versus grace) at each position, not about the shape of the plain-only curve across positions.

**Caveats.** This is a pilot, not the study: one cheap non-frontier model (`qwen/qwen3-30b-a3b-instruct-2507`) rather than the frontier backbones the main brief calls for, n=20 per cell rather than the 5-repeat, two-backbone design specified above, a single compaction event rather than the repeated-compaction regime that actually tests the "does repetition bake a rule in" mechanism, and a structured-decision proxy for violation rather than the deterministic tool-call grading a real agent harness would use. The result is real evidence that the mechanism exists and is worth a full study, not a finished result.

Script and raw per-trial records live in [`pilots/position-dependent-retention/`](pilots/position-dependent-retention/) in this repository, so the numbers above are reproducible rather than only asserted. Nothing has been committed to git; these are working-tree files pending review.

## F. Goal resurrection: sequence-ID anchoring

**Headline.** Tagging every stated task objective with a strictly increasing counter, and requiring a post-compaction summary to name and restate whichever objective carries the highest counter it saw, stops a summarizer from anchoring on a goal the user already replaced.

**Result (simplified version, run this session).** The design below, using SWE-Interact and a numeric tag, has not been run; what was run instead is a smaller, fully synthetic version (5 scenarios, single redirect, one backbone, 180 trials) using a prompt-level version of the same anchoring idea rather than an explicit numeric tag. It found something the design below did not anticipate: the vulnerable case is an *early*-issued redirect, not a late one (60% versus 95% correctly followed under plain summarization), and the anchoring fix repairs exactly that case (60% to 95%, p ≈ 0.02) while a generic wider-tail fix does not (p = 1). Full writeup in [`docs/paper/paper.pdf`](paper/paper.pdf) Section 5. The SWE-Interact-based, numerically-tagged version below is the natural next step to check whether the same pattern holds in a real coding harness with a genuine two-or-three-way goal chain rather than a single synthetic redirect.

**Benchmark.** Coding-agent transcripts where the task changes 2 to 3 times mid-session (a user redirect, or a subtask superseded by a later one), built by combining two pieces of existing, checked infrastructure: Supersede's task-construction pattern (arXiv 2606.27472, confirmed via direct fetch this repository already: state a fact, supersede it, test which value a bounded-memory agent reflects, code and a trained model publicly released) transplanted into SWE-Interact-style coding sessions (arXiv 2606.30573; its code, confirmed via direct fetch, is a 75-task, Apache-2.0-licensed benchmark on the Harbor harness, with a simulated user who progressively reveals requirements). Force a compaction event right after the latest goal change, and check whether the resulting summary's stated objective matches the newest goal or an earlier, already-replaced one.

**Open question that must be checked before relying on SWE-Interact here.** It has not been confirmed whether SWE-Interact's simulated-user revisions actually contradict an earlier instruction, as opposed to only adding detail to it. That has to be checked against the actual task files, not assumed from the paper's description, before building on it. If it turns out none of its 75 tasks contain a true contradiction, this benchmark needs its own synthetic supersession turns layered on top of SWE-Interact's coding tasks, which is a larger but still tractable fallback.

**Baseline.** Plain summarization with no goal-tracking mechanism, the default.

**Proposed method.** Three parts. First, every turn that states or restates an objective gets a strictly increasing integer tag. Second, the compaction prompt must name the highest-numbered tag it saw and restate that objective verbatim as "current objective" before summarizing anything else. Third, a cheap post-hoc validator, no extra model call needed beyond a string comparison, diffs the summary's stated current objective against the literal text of the most recent pre-compaction user message and flags a mismatch for one cheap re-ask.

**Metric and falsification.** Rate at which the post-compaction summary reflects the newest goal versus an older one, with and without the anchor, across compactors. Fails if the anchor does not reduce the stale-goal rate relative to plain summarization, or if SWE-Interact's revisions turn out not to be true contradictions as noted above.

**Compute budget.** Comparable to idea A once the SWE-Interact/Harbor harness is wired up; the harness setup is the main extra cost relative to A's fully synthetic design, and is worth doing once since F and (with less certainty) E can both use it.

**Related-work delta.** OpenAI's Codex repository, issue #45464 (found via search, not independently read), reports exactly this failure as an open, unattributed bug, which is itself evidence the mechanism is real and unstudied rather than already handled. Nothing found in this session's fresh searches changes this picture.

## B. Repair-compute vs. retention-compute crossover

**Headline.** At a fixed extra-token budget, spending it on self-verification repair passes and spending it on retaining more raw context are not interchangeable: repair only fixes mistakes where the needed fact is still physically present in the compacted summary, and its benefit plateaus within a handful of passes, while retention keeps paying off as compaction gets more aggressive. The crossing point between the two, in compression-ratio space, is a concrete number a team can use to decide where to put its budget.

**Benchmark.** Reuse idea A's synthetic transcripts with a ground-truth list of constraints at known positions. Compact each transcript at several compression ratios (for example, retain 70%, 50%, 30%, or 10% of tokens), plus an explicit zero-compaction control arm (needed because at high retention ratios almost nothing is deletion-type by construction, so the ratio sweep alone only implies a floor rather than measuring one). Label each constraint deletion-type (absent from the resulting summary) or retrieval-type (present, verbatim or paraphrased) by checking the summary text directly, using string or entailment matching, not the original transcript.

**Baselines.** A repair-only arm: re-prompt the agent, after compaction, to list and check for missing constraints, for 0 to 8 passes. The implicit baseline this whole idea argues against is the assumption, common in test-time-compute-scaling and self-refine or reflexion-style repair work, that inference-time repair is a generically useful lever whose returns depend only on task difficulty, not on whether the needed information still exists anywhere in the input.

**Proposed method.** The controlled, token-budget-matched comparison itself is the main contribution, since nobody has controlled for token parity between these two competing practitioner choices before, but a second, more actionable proposed method follows directly from its predicted result: a compute-aware compaction router that spends a fixed extra-token budget on retention while the compression ratio is above a measured threshold (few deletion-type errors expected) and switches to repair passes below it (more deletion-type than retrieval-type errors expected would make repair pointless, but the reverse composition, i.e. mostly retrieval-type errors at low compression, is where repair earns its keep). This router is what should be benchmarked against the two fixed-strategy arms as the paper's headline result, not just the diagnostic crossover curve.

**Metric and falsification.** Violation-rate reduction per token spent, split by error type; the location of the crossover in compression-ratio space. Fails if repair-pass count reduces deletion-type violations at a slope statistically indistinguishable from retrieval-type violations, which would mean repair passes are reconstructing content from general knowledge (confabulation) rather than surfacing it, undermining the retrieval/deletion distinction itself.

**Compute budget.** Similar order of magnitude to idea A, larger by the compression-ratio sweep and the repair-pass-count sweep, roughly 2 to 3 times as many cells; still inference-only and cheaply pilotable on the same OpenRouter setup used for A before spending frontier-model budget.

**Related-work delta, re-checked this session.** TokenPilot (arXiv 2606.17016, fetched and summarized this session) turns out to be about prompt-cache stability and serving cost under pruning, not about verification or repair at all; it does not compete with this idea. Self-GC (arXiv 2607.00692, fetched and summarized this session) uses a planner to decide what to fold, mask, or prune, i.e. when and how to compact, but, in its own summarized terms, "doesn't explore whether retaining more raw context to enable self-verification would outweigh the compaction savings." Neither controls for token parity between repair and retention, so the gap this idea targets still looks open at the abstract-and-method level checked here; a full line-by-line read of both is still worth doing before a pre-registration, but the provisional novelty case is now stronger than a search-only check would support.

## C. Recursive compaction ratchets away trigger-conditioned constraints

**Headline, revised this session.** A very recent paper, CliffCompaction (arXiv 2609.26779, posted days after this idea was first sketched), already shows that non-recursive, truncation-only compaction (each pass re-reads only the original content and discards the prior compacted output, never re-summarizing a summary) beats recursive, rephrasing-style compaction in aggregate on real coding benchmarks: up to 50% lower cost and over 10 points higher pass rate on Terminal-Bench, using real frontier-class backbones (Kimi K2.6, Opus, GPT-5.3 Codex). That result changes what this idea needs to show. It is no longer "does source-anchoring help," which is now answered; it is "is that aggregate win disproportionately driven by dormant, trigger-conditioned constraints specifically, in a way that compounds with round count," which CliffCompaction's evaluation did not isolate.

**What was checked and what was not.** CliffCompaction's abstract and method were fetched and summarized in this session (not fully read line by line); the summary found no mention of safety- or policy-style constraints, trigger-conditioning, or entity binding as an evaluated fact class. That is a gap in what is confirmed, not a confirmed gap in the paper itself, and should be checked by reading the paper directly before this idea's design is finalized.

**Benchmark.** Matched pairs of unconditional constraints ("never modify config.yml") and trigger-conditioned constraints ("if you ever touch config.yml, ask first"), at the same position and token length, with the trigger event engineered to fire at controlled distances after compaction. Cross two compaction regimes (recursive: re-summarize the prior summary each round; source-anchored, i.e. CliffCompaction-style: re-truncate from the original raw transcript each round) with compaction frequency (every 5, 10, 20, or 40 turns), matching total compaction events per regime, on roughly 200-turn synthetic transcripts (an extension of idea A's generator with a controllable trigger-firing delay).

**Baselines.** Recursive summarization (current common practice; the LangWatch trace study already cited in the main brief measured this in the wild on real Claude Code sessions). CliffCompaction's truncate-only regime, now a real, citable baseline instead of a hypothetical "source-anchored" strawman.

**Proposed method.** Not "source-anchoring is good," since that is now CliffCompaction's result, but a cheaper, targeted alternative that the original idea file already flagged as the realistic deployment path: selective re-anchoring, which keeps only trigger-tagged spans verbatim across rounds and re-summarizes everything else recursively, instead of re-reading the entire raw transcript every round the way full source-anchoring does. The claim to test: selective re-anchoring matches full source-anchoring's protection for trigger-conditioned constraints specifically, at a fraction of its per-round token cost, because it only pays the "re-read the original" tax on the small subset of content that actually needs it.

**Metric and falsification.** Violation and omission rate for trigger-conditioned versus unconditional constraints, by regime, by round count; token cost of full versus selective re-anchoring at matched protection level. Fails, per the original idea's own falsification conditions, if erosion does not scale with round count at a fixed trigger distance, or if the source-anchored regime shows equal-or-worse erosion than recursive, which would mean the regime axis is not what is doing the work.

**Compute budget.** Meaningfully higher than idea A: round-count sweeps up to 40 rounds on 200-turn transcripts multiply the cell count by roughly 5 to 8 times. Recommended: pilot at reduced scale first (50-turn transcripts, up to 8 rounds) on the same cheap OpenRouter setup used for idea A, before spending frontier-model budget on the full sweep.

## D. Ratchet vs. rescue (merge of B and C)

Unchanged in substance from the original idea file, with one update: its closest prior work is now the same CliffCompaction paper named in idea C's revised section above, not a generic "recursion-depth account." The idea uses B's token-budget-matched repair-versus-retention split as a diagnostic instrument on constraints already damaged by C's ratchet mechanism, to distinguish genuine deletion (repair cannot rescue it) from mere retrieval failure (repair can). As the original idea file itself notes, this is a four-way design (regime by frequency by repair-versus-retention arm by constraint type) that is higher-risk to interpret than either parent alone, so it should only be run after B and C's individual predictions have been checked separately; a failure in the combined design would otherwise be hard to attribute to one mechanism or the other.

## E. Cheap stand-in for rollout-based compaction validation

**Headline.** Two or three extra draft summaries of the same history, checked against each other for agreement on load-bearing facts, might predict what an expensive TRACE- or Slipstream-style paired continuation would catch, at roughly a tenth of the compute.

**Benchmark.** At each simulated compaction point in a transcript (idea A's or C's generator can supply these), compute two things: the expensive reference signal, a short paired continuation from full context (two independent continuations, checked for divergence, exactly TRACE's and Slipstream's method), and the cheap candidate signal, two or three draft summaries of the same history checked against each other for disagreement on file names, decisions, and remaining work. Measure how well the cheap signal's disagreement flag predicts the expensive signal's divergence flag across many compaction points.

**Baselines.** The paired-continuation gate itself (expensive, roughly doubles compute at the compaction boundary), and doing no check at all (today's default).

**Proposed method.** The draft-agreement gate as already specified in the original idea file. The "beats current methods" framing is a Pareto argument, not a strict improvement: the goal is a point strictly better than either extreme, catching a useful fraction of what the expensive gate catches at a small fraction of its cost, not matching it exactly.

**Metric and falsification.** Precision and recall of the cheap gate's flags against the expensive gate's divergence labels, and the cost ratio between them. Fails if the two are uncorrelated, meaning draft agreement is measuring something other than actual downstream execution divergence.

**Compute budget.** Modest: roughly 3 to 4 times the cost of a single ordinary compaction event (two continuations plus two or three drafts), cheaply pilotable on the same setup used for idea A.

**Related-work delta.** Unaffected by this session's new findings. Context Codec (arXiv 2605.17304, reported as verified by a research fork in the original idea file, not independently re-confirmed here) remains the closest existing sketch, five hand-scored examples on single-document compression, not agents, so the agent setting is still open. ## G. Drift detection linked to automatic rollback

Unchanged in substance from the original idea file and still the lowest-priority idea here, for a concrete reason confirmed by everything else in this document: A, B, C, D, E, and F can all run on synthetic transcripts with no real repository, no real git history, and no code execution, which is why they are cheap and fast to pilot. This idea cannot: it needs a real small repository, real commits made in response to a planted false belief, and a scheme for attributing a specific commit to a specific belief, which is a harder engineering problem than any of the others here and the likeliest of the seven to produce a noisy or ambiguous first result. It is worth returning to once the shared transcript-generator infrastructure from the other ideas exists and there is a natural way to extend it with an actual sandboxed repository.

## What was not done in this session

No paper has been read in full; every claim above sourced from a fetch or search this session is explicitly marked as abstract-and-method-level or search-only, following this repository's existing standard. In particular, CliffCompaction (arXiv 2609.26779) deserves a full read before idea C (and D, which depends on it) is finalized into a pre-registration, since its abstract-level summary did not settle whether its evaluation includes anything like a safety- or policy-style constraint. The pilot in this session covers only idea A, and only its single-compaction-event version, not the repeated-compaction mechanism the full design calls for.
